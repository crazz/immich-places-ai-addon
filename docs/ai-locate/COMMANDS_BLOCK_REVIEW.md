# Огляд Commands Block для Immich Places AI Add-on

Огляд стосується [адаптованого мастерпромпту](MASTERPROMPT_CH02_CH03.md) для **CH02 → CH03, потім зупинка**. **Статус: усі три зміни нижче внесено в Commands Block за прямою вказівкою користувача.** Project Block узгоджено з оновленим текстом. Оригінальне вкладення збережено; підготовка документів не запускає реалізацію changes.

## 1. Усунено обов'язкове делегування та вимогу іншого агента-reviewer

**Де:** C1, пов'язані рольові інструкції C2, передача власності C4 і handoff/review C5.

Приклади з оригіналу:

> Він не пише реалізаційний код; делегує код, тести та змістовні документаційні зміни виконавцю.

> Reviewer не є тим самим агентом, який написав реалізацію.

> Для нового change використовуй свіжих субагентів із мінімальним релевантним контекстом.

Ці інструкції оригіналу суперечили вашій чинній вказівці: **«Dont use subagents, entire process (code, review, tests) - here»**. В оновленому Commands Block прибрано делегування, fresh/reused агентів і передачу build/test ownership іншому агенту.

**Внесений контракт C1, стисло:**

> Усі етапи виконує один поточний агент у цій розмові: декомпозиція, реалізація, тести, перевірка відповідності специфікації, перевірка якості, виправлення та Git/CI. Субагентів не використовуй без нової прямої вказівки користувача. Збережи поточні налаштування моделі й reasoning. Після цілісної реалізації окремо перевір актуальний diff і достатність доказів; не називай самоперевірку незалежним review. Збери відомі суттєві зауваження одним пакетом, виправ їх і повторно перевір зачеплені місця.

**Пов'язані внесені зміни:**

- C2: один агент формує декомпозицію і перевіряє її повноту до коду. Карта контракту та контрприклади збережені.
- C4: замість передачі власності між агентами — стабільний snapshot без редагування inputs до завершення перевірки. Правила оточення, exit codes і повторного використання актуального green залишаються.
- C5: `handoff` замінено внутрішнім checkpoint доказів перед review. Прибрано вимогу іншого reviewer; передбачено окремі проходи spec review і quality review одним агентом. Збережено перевірку сценаріїв, boundaries, fault paths, readiness і наслідків виправлень.
- C3/C6/C8: прибрано залишкові посилання на субагентів, handoff та окремі звіти виконавця/reviewer; докази й автономність збережені.

P3 і Commands Block тепер узгоджені: увесь процес тут, одним агентом, без заяв про незалежність самоперевірки. Обхідний виняток для суперечливих команд більше не потрібний.

## 2. Уточнено TDD для всієї нової або зміненої поведінки

**Де:** C3, замінено абзац, який починався «Для виправлення дефекту виконавець спочатку додає й запускає тест…».

Попередній текст явно охоплював лише defects. Оновлений відповідає [testing standard](../engineering/testing.md#test-writing-rules): OpenSpec Plus TDD для **нової або зміненої поведінки**, включно з новими CH02/CH03 capabilities.

**Внесений абзац:**

> Для нової або зміненої поведінки, включно з виправленнями дефектів, дотримуйся RED → GREEN → REFACTOR: спочатку додай один поведінковий тест, побач його падіння з очікуваної причини на поточній реалізації, внеси мінімальну production-зміну, отримай green і оціни потребу refactoring перед наступним тестом. Characterization відомої наявної поведінки може пройти одразу. Не створюй штучні регресії, не мутуй тимчасові копії й не вимагай mutation testing. Помилки harness, імпортів, collection або оточення не є meaningful RED.

P6 також оновлено: більше немає застарілого застереження про вужчий контракт C3.

## 3. Уточнено різницю між картою blast radius і symbol impact

**Де:** фінал C2: «Не повторюй його після кожного редагування».

У контексті C2 це загальна карта впливу change. Додано уточнення, щоб фразу не прочитали як скасування обов'язкового GitNexus аналізу з [AGENTS.md](../../AGENTS.md).

**Внесене доповнення:**

> Це правило стосується повторного складання всієї карти change. Обов'язкові GitNexus impact перед редагуванням наявних символів і detect_changes перед commit виконуються за Project Block та AGENTS.md.

Це узгоджено з **P4**; переписувати або повторювати весь graph analysis після кожної дрібної правки не потрібно.

## Збережені правила

- **C2/C5: карта сценарій → entry point → assertion.** Корисна для egress authorization, DNS/dial boundaries, revocation, CAS і UI states. Підтримуй одну компактну карту; окремий тест на кожен її рядок не вимагається самим текстом.
- **C5: «Якщо зламати саме це з'єднання, який assertion упаде?»** Це питання для аналізу достатності тесту, а не наказ фізично ламати код чи виконувати mutation testing. Для відомої UI-поведінки достатньо звичайних characterization tests.
- **C3: architecture checks і production initialization.** Для цього репозиторію використовуються наявні dependency checks, Go build/import rules і real SQLite migrations. Новий універсальний framework не потрібний.
- **C4: повний gate, preflight і lock checks.** Набір уже визначає Project Block: штатні Go/Bun/Next/Playwright перевірки. Команди та особливості .NET були лише в старому Project Block і замінені там. Для documentation-only closure діє P5; remote CI лишається обов'язковим.
- **C6: окремі спроби й receipts.** Підходить; P9 задає ignored `out/execution/`, фактичні команди/exit codes та точний SHA. Нового runner або окремої інфраструктури журналювання це не потребує.
- **C7: без зайвого closure commit.** Підходить. Слово `deploy` у формулюванні про належні перевірки не авторизує deployment: обсяг визначає P10, і в цьому batch deployment відсутній.
- **C8: автономність у погоджених межах.** Підходить; межа — завершити CH02 і CH03, після чого зупинитися.

- SHA-256 оригінального Commands Block: `14599d7367eee3db19997ac57d0ab3bb9c7227b8a29e0e3581a2d7da98bfbacf`.
