### P4. GitNexus, інфраструктура та документація

Використовуй GitNexus для repo `immich-places-ai-addon` за актуальним AGENTS і [workflow аналізу](../engineering/architecture.md#codebase-analysis-and-change-verification). Спочатку звір шлях, checkout, індексовану ревізію та незакомічені зміни коду. `query` — концепції/flows, `context` — символ, `impact` upstream — до редагування наявної функції, класу чи методу. Повідом callers, processes і risk; HIGH/CRITICAL — до редагування. UNKNOWN або порожній граф не доводять безпеку: перевір прогалини за source/tests.

Перед кожним commit виконуй `detect_changes(scope: all)`; для regression review — `scope: compare` з точним зафіксованим SHA бази change. Partial/truncated результат не є clean. Якщо інструмент не охопив untracked файли або міжмовні/динамічні зв'язки, явно перевір їх і познач межу доказу. Оновлюй застарілий індекс за чинним AGENTS і GitNexus skill. Documentation-only правки не потребують штучного symbol-impact, але pre-commit change analysis залишається обов'язковим.

Загальна карта blast radius оновлюється при зміні контракту, рішення або ownership; це не скасовує обов'язкового impact перед редагуванням символів. Не повторюй весь аналіз без нового предмета перевірки. Перейменування символів роби засобом GitNexus `rename`.

GitHub Actions перевіряй через наявний `gh` або доступний connector на точному commit SHA. Не змінюй CI заради економії й не створюй новий adapter для штатних Git/CI операцій. Документацію технологій отримуй через Context7 за актуальним AGENTS, коли питання потребує актуального API/SDK/CLI контракту; виконуй його правила library → docs та оточення.

На uGreen NAS уже працює контейнер `codex_proxy`; використовуємо його, **новий proxy-контейнер не створюємо**. Перевірена топологія: Docker network `npm_proxy`, alias `codex-proxy`, endpoint для backend у цій мережі — `http://codex-proxy:3466/v1`. Loopback усередині backend-контейнера не означає proxy-контейнер. Deployment цього addon branch на NAS не підтверджений.

Наявний proxy default — `gpt-5.6-luna`; перший кандидат сильнішої моделі для addon profile — `gpt-5.6-sol`. Сумісність Sol із цим endpoint ще не перевірено. Вибір моделі роби в профілі addon; глобальний default proxy не змінюй. CH02 вимагає явного operator approval для точного HTTP endpoint і обмежених адрес мережі; історична Docker subnet не є універсальним дозволом. Перед майбутнім deployment повторно звір топологію. Жодного автоматичного fallback, перемикання моделі чи live-запиту під час звичайних тестів.

### P5. Наявні перевірки та оточення

Використовуй штатний runner і команди з [testing standard](../engineering/testing.md). Toolchains, закріплені в CI: Node.js `22.23.2`, Go `1.25.14`, Bun `1.4.2`. Перевір наявність залежностей і pinned Playwright Chromium; встановлюй їх штатними командами за потреби, не змінюючи lockfiles побічним ефектом. Не створюй новий test runner.

На початку кожного change зафіксуй фактичний Git SHA його бази як `CHANGE_BASE` у brief/receipt. Для CH03 це база після завершення CH02. Використовуй цей SHA для порівняння всього change; пізніший `HEAD` не має приховувати вже закомічені зміни.

Команди з кореня репозиторію; `$CHANGE_BASE` має містити цей перевірений SHA:

```bash
bun run check --base "$CHANGE_BASE"
bun run check --gate go-tests --base "$CHANGE_BASE"
bun run check --gate frontend-tests --base "$CHANGE_BASE"
bun run check --gate smoke --base "$CHANGE_BASE"
bun run check:size --base "$CHANGE_BASE"
bun run check:dependencies --base "$CHANGE_BASE"
```

Перший рядок — повний gate; решта — варіанти цільового запуску за потреби, а не обов'язкові повтори після full pass. Повний runner охоплює 13 gates: checker tests, size, dependencies, gofmt, lint, route type generation, TypeScript, Go vet, Go race tests із coverage, frontend tests із coverage, Go build, frontend build і browser smoke. Focused frontend запуск: `bun run test:unit <фактичний test path>`. Прямі Go перевірки виконуй з `backend/` за testing standard.

Після нового коду потрібний актуальний успішний повний gate; якщо він уже підтверджує незмінений фінальний стан, не повторюй його лише через перехід до review/commit. Для чистого sync/archive або іншої documentation-only правки локально достатні відповідні document/configuration/OpenSpec checks; обов'язковий CI на новому SHA зберігається. Container build додавай, коли змінюються відповідні build/deployment inputs.

Не редагуй inputs під час перевірки. Yielded команду продовжуй за її session ID, не запускай дублікат. Sandbox/toolchain/browser помилки фіксуй як помилки оточення, не як дефект продукту; виправ оточення і повтори зачеплений gate. Дозволи виконання визначай за фактичною потребою, без успадкованих винятків іншого проєкту. Зберігай кожну спробу за P9.

### P6. Архітектурний і тестовий контракт addon

Збережи Go/Next.js/SQLite deployment та існуючі manual/GPX workflows. Нове AI core — у focused packages `backend/internal/ai/`; конкретні I/O adapters — у дозволених архітектурою integration locations, зокрема `backend/internal/aiadapters/` або focused root `backend/ai*.go`; AI UI/state — `src/features/ai/` з його public boundary. Не додавай сервіс, брокер, ORM або нову систему конфігурації без потреби контракту.

Handwritten source **і tests — максимум 500 фізичних рядків**, включно з comments/blanks. Точні inherited exceptions, ratchet та exclusions бери з coding standard; новий файл не успадковує виняток, а чинний over-limit файл не може зростати відносно change base або adoption ceiling. Діли за відповідальністю.

Для нової або зміненої поведінки використовуй OpenSpec Plus TDD: meaningful RED → мінімальна реалізація → GREEN → оцінка refactoring, по одному тесту. Characterization відомої наявної поведінки може одразу бути green. **Не роби штучні регресії, мутації тимчасових копій або обов'язковий mutation testing.** Помилка імпорту/harness не є meaningful RED. Послідовність визначено також у C3.

Кожен поведінковий OpenSpec scenario має автоматизований доказ на відповідному рівні. Використовуй real file-backed SQLite та production migrations для тверджень про persistence, upgrade/reopen, tenant isolation, CAS і cleanup. Provider/handler tests — через реальні adapters та local HTTP fixtures; рахуй заборонені виклики й перевіряй точний payload. UI — Vitest/RTL; end-to-end — Playwright із built Next.js, реальним Go backend і SQLite, synthetic external fixtures.

Мінімум AI coverage: Go statements 80%; TypeScript lines і branches 80%, включно з untested files у визначеному standard scope. Відсоток не замінює перевірку failure/security paths. Контролюй час і конкурентність clocks/barriers/channels; доводь readiness перед release/cancel, забезпечуй cleanup без залежності від успішності assertion.

Analysis і draft acceptance не мають права змінювати Immich; майбутній confirmed writer працює лише за durable revision-bound планом точних approved assets/fields. CH02/CH03 не додають writer або аналіз приватних фото. Перевір нуль небажаних Immich/provider effects, ownership/session/revision checks, disablement, credential removal, cancellation і безпечні помилки. Збережи AI-disabled journeys та CH01 settings behavior.

Звичайні тести offline, із synthetic даними. Окрема live compatibility перевірка може довести лише реально виконаний endpoint/model contract. Її відсутність позначай як `не перевірено`; fixture pass не закриває GATE-03 для NAS.

### P8. OpenSpec та цикл публікації

Для кожного change: актуальні зелені локальні gates і завершене inline review → implementation commit → push у `codex/engineering-foundation` → успішні обов'язкові CI checks на точному implementation SHA → `openspec-sync-specs` → перевірка повноти merged main specs → `openspec-archive-change` → archive commit → push → успішні обов'язкові CI checks на точному archive SHA.

Sync/archive виконуй за відповідними skills; збережи `.openspec.yaml`, артефакти та незмінені requirements/scenarios main specs. CH03 має доповнювати вже синхронізований CH02 і зберігати CH01; не замінюй весь provider spec дельтою CH03. Позначай tasks виконаними лише за фактичними доказами всіх підсценаріїв. Перевір strict validation, scenario/test traceability та актуальність посилань після перенесення в archive.

Оновлюй поточні status/links у roadmap та index під час звичайних implementation/archive commits. Історичні P2 цього промпту залишай датованим checkpoint. Після archive CI зафіксуй receipt без нового commit лише заради post-CI запису. Не змінюй pipeline і не пропускай gates для прискорення.

Після CH02 виконай CH03. Після CH03 наступна дія — звіт і зупинка, навіть якщо решта roadmap має ready candidates. Merge, deployment та live model evaluation не входять у цей цикл.

## Commands Block

### C1. Один агент, етапи роботи та контекст

Усі етапи виконує один поточний агент у цій розмові: декомпозиція, архітектурні рішення, реалізація, тести, документація, перевірка відповідності специфікації, перевірка якості, виправлення та Git/CI в межах Project Block. Субагентів не використовуй без нової прямої вказівки користувача. Збережи поточні налаштування моделі й reasoning.

Після цілісної реалізації окремо перевір актуальний diff і достатність доказів за C5; не називай самоперевірку незалежним review. Збери відомі суттєві зауваження одним пакетом, виправ їх і повторно перевір зачеплені місця.

Для кожного change визнач конкретний результат, потрібні шляхи й контекст, дозволені межі редагування та критерії готовності. Використовуй готові scripts/helpers і потрібні skills для типових операцій, з точними параметрами та правилами оточення з обох блоків. Не створюй повторно наявний спосіб запуску тестів.

При переході до наступного change онови контекст за його артефактами та фактичним landed API. При відновленні роботи звір актуальний diff, журнал і докази; завершене повідомлення саме по собі не означає завершення change.

### C2. Контракт і blast radius до кодінгу

Для кожного change прочитай актуальні вимоги й контекст за workflow із Project Block. Сформулюй короткий контракт: проблема, потрібна поведінка, інваріанти, межі зміни та перевірки. Для складної зміни зроби короткий архітектурний огляд до кодінгу.

До вибору цільових тестів і до реалізації почни одну компактну карту в наявних tasks/brief або короткому повідомленні й веди її до внутрішнього checkpoint доказів за C5. Перелік сценаріїв походить з authoritative tasks/specs, а не зі списку вже написаних тестів. Складений task розділи на незалежно порушувані обов’язкові результати чи гілки поточного scope. Для кожного покажи:

```text
task / сценарій / інваріант → реальний entry point → прямі й похідні consumers
→ кінцевий результат → запланований test/case та assertion → підмінені boundaries
```

На C2 test/case та assertion можуть бути запланованими; це ще не доказ виконання. Під час роботи доповнюй ту саму карту фактичними доказами й статусами за C5. Один тест або параметризований harness може підтверджувати кілька рядків; окремий тест на кожен рядок не вимагається. Для неповедінкової вимоги використовуй придатний доказ замість штучного тесту. Явні відкладення scope записуй окремо. Великого додаткового документа не потрібно.

У blast-radius аналізі встанови:

- які поведінка, формати даних, API, configuration, ownership або persisted state змінюються;
- які callers, агрегації, переходи стану, recovery та повідомлення оператору від них залежать;
- які fixtures, stubs, очікування, corpus і prompt-seam tests залежать від старого контракту;
- де повнота впливу залишається непідтвердженою.

Шукай залежності також через ідентифікатори даних, case IDs і тестові очікування. Для кожного consumer визнач: він має слідувати поточному контракту, зберігати історичний контракт чи перевіряти сумісність. Не оновлюй усі tests механічно до поточного input/oracle, якщо це спотворює історичні докази.

Після видалення або перенесення production-виклику переоцінюй пов’язані mocks, fixtures і сценарії тестів. Не зберігай production-імпорти, exports або lint exceptions лише для підтримки застарілої тестової підміни без окремого обґрунтованого compatibility-контракту.

Коли змінюєш контракт володіння, зупинки або cleanup, перевір його реалізації, обгортки та шляхи створення. Обов’язкова операція має виконувати заявлену дію; обгортка — передавати нові обов’язки; спільна залежність — передаватися явно. Не залишай default success без дії або compatibility fallback, який мовчки створює іншого власника. Зручне створення об’єктів для тестів тримай у тестових fixtures; фактичний ефект перевіряй за C5.

Коли зміна додає або змінює блокування на межі з бібліотекою чи callback, перевір порядок захоплення locks у прямому виклику та зворотному callback, включно з shutdown/dispose. Покажи короткий контрприклад можливого взаємного очікування або поясни, чому цикл неможливий.

Якщо кілька правил можуть одночасно застосовуватися до одного входу, у декомпозиції явно визнач їхній пріоритет та очікуваний результат на перетині. Для змін переходів стану склади компактну таблицю:

```text
поточний стан × суттєвий тип входу × умова прийняття
→ зміна стану та дозволені побічні дії
```

Не вважай перевірку кожного правила окремо доказом правильності їх поєднання; явно перевіряй випадки їх одночасного застосування.

Простеж цей інваріант через усі виявлені шляхи зміни відповідного стану, включно з попередніми upsert, helpers, callbacks і наступними побічними діями. Непідтверджені шляхи познач явно.

Для кожної нової обов’язкової передумови переходу визнач producer, умови його роботи та область відповідальності. Перевір очікувану поведінку, коли потрібні дані не виробляються. Розрізняй producer, вимкнений за конфігурацією або поза scope, і producer, який тимчасово недоступний.

Перевір, що декомпозиція охоплює обов’язкові історії та суттєві залежності. Для перетинів правил сформулюй один конкретний контрприклад, де одне правило дозволяє зміну, а інше має її заборонити. Покажи очікуваний результат і місце цього випадку в таблиці до реалізації.

Це короткий внутрішній checkpoint, не повне code review. Звичайні рішення не потребують нового погодження користувача. Прогалини виправляються до реалізації; запропонований test ID ще не є доказом існування або проходження тесту.

Оновлюй blast-radius аналіз, якщо під час реалізації або review змінюється рішення, спільний контракт чи ownership. Не повторюй його після кожного редагування. Оновлення має передувати новому твердженню про достатність цільових перевірок.

Це правило стосується повторного складання всієї карти change. Обов'язкові GitNexus impact перед редагуванням наявних символів і detect_changes перед commit виконуються за Project Block та AGENTS.md.

- Для символів, декларацій, references, callers та implementations спершу використовуй графовий інструмент із Project Block. До редагування символів виконуй визначений там impact analysis та повідомляй ризики; не підміняй його текстовим пошуком.
- Створюй і змінюй файли вбудованими засобами редагування (`apply_patch`); для перейменування символів використовуй спеціалізовану операцію, визначену в Project Block.
- Читай лише потрібні bodies. Для top-level shell/non-code використовуй потрібні діапазони.
- `rg` використовуй для літералів, конфігурації, логів і переліків файлів; для залежностей коду — щоб доповнити порожній або `UNKNOWN` результат графа. `grep` — за відсутності `rg`.
- Не повторюй успішні retrieval широким читанням без конкретної потреби.
- Дотримуйся правил документації технологій, визначених у Project Block та актуальних інструкціях репозиторію.

Для нової або зміненої поведінки, включно з виправленнями дефектів, дотримуйся RED → GREEN → REFACTOR: спочатку додай один поведінковий тест, побач його падіння з очікуваної причини на поточній реалізації, внеси мінімальну production-зміну, отримай green і оціни потребу refactoring перед наступним тестом. Characterization відомої наявної поведінки може пройти одразу. Не створюй штучні регресії, не мутуй тимчасові копії й не вимагай mutation testing. Помилки harness, імпортів, collection або оточення не є meaningful RED.

Кожну user-visible story перевіряй через реальні модулі на рівні, визначеному Project Block. Використовуй production-ініціалізацію стану та спільний integration harness, коли цього потребує контракт. Підміняй лише явно дозволені зовнішні межі; не підміняй поведінку, яку цей тест має довести. Результат на підміненій межі не доводить виконання за нею. Створення тестового сховища без assertion кінцевого результату роботи зі станом не доводить integration coverage.

Для тесту помилки підтверди, що запланована помилка фактично виникла, і перевір кінцевий результат її обробки.

Час контролюй через визначені проєктом helpers/керовану синхронізацію, без sleep у тестах. Не замінюй production schema спрощеною вручну створеною схемою, крім навмисних сценаріїв пошкодження чи відсутності.

Нові модулі й залежності перевіряй architecture tests рано. План перевірок визначається blast radius, а не лише списком відредагованих файлів.

Не розширюй change сторонніми покращеннями. Необхідні блокери коректності та безпеки виправляй у поточній роботі; інші ідеї стисло фіксуй окремо.

### C4. Повний gate та оточення перевірок

Виконуй повний gate, preflight, lock checks та validation, визначені в Project Block. Використовуй сумісне тестове оточення. Sandbox permission errors діагностуй як помилки оточення; не змінюй коректний код або assertions, щоб приховати їх.

Якщо blast radius широкий або його повнота непевна, запусти ранній повний gate на першому цілісному зрізі до пакетного review. Не чекай завершення всіх раундів review, щоб отримати перший широкий feedback. Зафіксуй snapshot і не редагуй inputs перевірки до завершення команди. Залишайся відповідальним за власні тестові процеси та їх cleanup; не змішуй докази різних станів коду.

Перед повним gate на ізольованому snapshot забезпеч передумови всіх його перевірок, включно з потрібним Git-контекстом, залежностями та локальними sockets. Hashes коду не доводять готовності оточення.

Помилки оточення виправляй із повтором зачеплених перевірок на тому самому коді; зберігай первинний результат і результат повтору окремо.

Після стабілізації остаточний diff має чинний успішний повний gate. Якщо ранній gate уже зелений і відтоді не було релевантних змін, нових помилок чи конкретної невирішеної загрози, не запускай його знову лише через зміну етапу роботи. Обов’язковий CI зберігається.

Перед кожним commit виконай аналіз змін графа за Project Block. Неповний результат аналізу не є успішною перевіркою; він не замінює повний gate або CI.

### C5. Внутрішній checkpoint доказів і review

Перед review доповни карту з C2 фактичними доказами. Це внутрішній checkpoint одного агента. Для поведінкового рядка потрібні:

```text
task / обов’язковий сценарій → конкретний test/case → фактично досягнута умова або гілка
→ кінцевий assertion → статус
```

Межу підміни позначай, якщо вона обмежує твердження. Статуси: `підтверджено` / `частково` / `немає доказу`. Task можна позначити `[x]` лише після підтвердження всіх його обов’язкових підсценаріїв поточного scope; `частково` та `немає доказу` залишають його відкритим, навіть якщо всі запущені тести зелені. Явне відкладення scope не видавай за виконаний сценарій.

На першому checkpoint звір повноту від authoritative tasks/specs до карти, потім перевір у harness і коді тестів заявлену гілку, реальні модулі, boundaries та кінцевий assertion. Назви тестів або попередній звіт — покажчики на докази. Спільний параметризований harness читай один раз разом із потрібними cases. Для нового чи зміненого з’єднання між шарами відповідай: «Якщо зламати саме це з’єднання, який assertion упаде?» Перевірка суміжного шару не закриває неперевірене з’єднання.

Після виправлень оновлюй і звіряй зачеплені рядки карти та їхні наслідки; повторно використовуй достатні актуальні докази. Це уточнення checkpoint не додає окремого повного review або великого документа.

Контрприклад із декомпозиції звір із фактичним тестом: реальний entry point, досягнення потрібної гілки та кінцеві assertions стану й побічних дій. Самої назви тесту або наявності окремих перевірок обох правил недостатньо. Для fault-path test перевір фактичне спрацювання запланованої помилки та результат її обробки.

Для тестів із керованим часом або навмисною гонкою перед clock advance, EOF, exit чи release перевір часову передумову: що саме доводить readiness signal, хто його виробляє та чи може він спрацювати передчасно або від іншої події. Ця перевірка стосується відповідних тестів; вона не вимагає нових універсальних gates або повторних stress runs.

Для операційних scripts/helpers прив’язуй доказ до hash виконаної версії, команди та незміненого output. Після зміни helper познач зачеплені попередні докази як історичні й посилайся на актуальний запуск. Перевір цю відповідність під час review. Якщо актуальний запуск уже підтверджений, виправ посилання на доказ; якщо його немає — виконай потрібну перевірку.

Після цілісної реалізації, зелених цільових перевірок та checkpoint доказів виконай окремі проходи перевірки відповідності специфікації та якості коду. Перевір актуальний diff і реальні докази; це самоперевірка одного агента, не незалежне review. Збери всі відомі суттєві зауваження одним пакетом, включно з релевантними failures інших перевірок, щоб виправити їх разом.

Для regression review використовуй порівняльний аналіз графа з Project Block разом із цільовою перевіркою коду й тестів.

Виправ пакет зауважень. Повторне рев’ю перевіряє виправлення та їхні наслідки. Повний повторний аудит потрібний лише за новими доказами ризику.

Перед інтеграцією підтвердь повноту контракту, закриття критичних зауважень, достатність доказів і межі diff. Повторно використовуй актуальні висновки review без повного дублювання перевірок.

### C6. Докази та структурований receipt

Для кожного доказового значення визнач об’єкт, етап отримання та властивість, яку перевіряєш. Розрізняй незмінність файла і збереження логічних даних. Вимагай побайтової рівності різних артефактів лише тоді, коли це передбачає контракт; однакові назви полів такої вимоги не встановлюють.

Кожну спробу перевірки зберігай окремо; повторний запуск не має перезаписувати попередній результат. У checkpoint доказів посилайся на потрібну спробу.

Авторитетний результат CI — перевірений стан точного run разом із його artifacts і прив’язкою до commit/tree. Репозиторний журнал є checkpoint фактів, відомих на момент його commit; він не може наперед містити результат CI цього самого commit.

Після потрібного CI перевір результат і збережи окремий структурований receipt поза версійованими файлами, у місці з Project Block. Не покладайся лише на `/tmp` або текст чату. Зберігай посилання на CI та незмінені завантажені докази, щоб їх можна було повторно звірити.

Використовуй формат receipt із Project Block. Прив’язуй висновки до перевірених джерел, точної версії та етапу роботи.

Відсутні дані позначай як непідтверджені, а не як success чи нуль. Зберігай failed reports і попередні receipts; новий успішний run не переписує історію невдалого. Receipt узагальнює перевірені джерела, а не самостійно надає довіру неперевіреному результату.

### C7. Журнали та завершення без додаткового closure release

Дотримуйся релізного порядку й умов завершення з Project Block. Оновлюй визначені там журнали, зберігаючи порядок плану та сумісність структури. Версійовані checkpoints оновлюй під час звичайних implementation/lock/archive commits; локальні журнали й receipts залишай поза commits та оновлюй одразу після перевірки фактів. Фіксуй лише вже відомі факти. Якщо останній CI ще попереду, явно поясни, що це checkpoint до CI та що остаточний результат визначається точним run і receipt.

Коли після archive CI з’явилися нові факти:

- перевір їх і запиши receipt; на цій підставі визначай фактичне завершення change;
- якщо проєкт має версійований checkpoint і робота продовжується, перенеси підтверджене закриття в наступний звичайний робочий commit; локальний журнал онови одразу;
- при паузі або завершенні плану не створюй окремий commit/push/deploy лише для заміни pending на success чи запису номера щойно завершеного CI;
- у фінальному повідомленні дай точний commit, результат archive CI, посилання на перевірені докази та стан наступного change;
- при відновленні спершу звір checkpoint із CI/receipt. Застарілий pending сам по собі не є підставою повторювати успішний release.

Не роби чистоту або актуальність post-CI запису саме в релізній гілці додатковою умовою завершення, що породжує новий closure release. Останній commit усе одно має пройти весь належний CI/deploy/confirmation; це правило змінює місце фіксації результату, а не скасовує перевірки. Реальний release blocker виправляється звичайним перевіреним commit.

### C8. Комунікація та автономність

Звіти про реалізацію, перевірки та review — стисло:

- що змінено та в яких файлах;
- що фактично перевірено: test IDs/команди, results і посилання на докази;
- що залишилося неперевіреним або незавершеним.

Сила твердження не перевищує силу доказу. Зелені тести не доводять повноту контракту. Відсутність збігів пошуку не доводить відсутності структурних порушень, якщо покриття пошуку не встановлено. Не стверджуй «усі stubs видалено» або «всі consumers перевірено» на підставі неповного пошуку чи лише наміру зроблених редагувань.

Не повторюй у кожному повідомленні весь план, великі JSON, повні логи та hashes. Посилайся на збережені докази й витягуй потрібні поля. Під час довгих операцій давай короткий змістовний статус.

Виконуй уже авторизовані в Project Block дії без повторного погодження звичайних кроків. Внутрішня перевірка декомпозиції або checkpoint доказів не є новим approval flow для користувача.

За реального блокера спочатку виконай незалежну доступну роботу, потім постав одне конкретне питання про відсутню інформацію чи доступ. Не приховуй незавершеність і не вигадуй докази.

Продовжуй до завершення обсягу Project Block, якщо оператор не змінить scope або не попросить зупинитися.
