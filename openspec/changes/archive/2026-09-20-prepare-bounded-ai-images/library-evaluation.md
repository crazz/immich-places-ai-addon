# CH08 image-library evaluation

20 September 2026. The owner approved `imaging + x/image` after reviewing the alternatives and existing Sharp dependency. The selected versions are imaging v1.6.2 and x/image v0.45.0, including the existing-module upgrades described below. The selected dependencies are installed in the application module; full verification is recorded with CH08.

CH08 needs bounded raster decoding, orientation normalization and downscaling without adding a service or modifying original files. Network authorization, byte/pixel budgets and cancellation remain application responsibilities regardless of the library.

## Existing project capabilities

- `sharp v0.34.5` is already resolved in `bun.lock` and installed locally as an optional transitive dependency of Next.js 16.1.6. It is not a direct application dependency or an existing AI image-preparation service. Sharp can auto-orient, resize and encode images; output metadata is removed by default unless preservation is requested.
- The photo grid, album thumbnails and lightbox explicitly use `next/image` with `unoptimized`. No direct Sharp imports were found in application source. The Go preview and thumbnail handlers currently stream Immich responses without a local normalization pipeline.
- Go's standard library supplies JPEG/PNG codecs without an additional module, but not the complete requested WebP, resizing and EXIF auto-orientation workflow. The existing indirect `mimetype` dependency detects file types; it is not an image transformer.
- The frontend runs in Node, while `backend/Dockerfile` builds with `CGO_ENABLED=0` and its runtime contains neither Node nor libvips. Reusing Sharp for backend jobs would require an explicit processing boundary with the existing Node service, or a backend packaging change. It is a viable architectural alternative, but its presence in the frontend dependency tree does not make it callable from Go.

## Candidate comparison

| Candidate | Maintenance, compatibility and license | Fit and trade-offs |
|---|---|---|
| `github.com/disintegration/imaging v1.6.2` with `golang.org/x/image v0.45.0` | Imaging is MIT, latest tagged release November 2019, repository last pushed September 2023, approximately 5758 stars when inspected. x/image is the BSD-3-Clause Go image module, actively updated; v0.45.0 supports Go 1.25, while v0.46.0 requires Go 1.26. | Recommended pure-Go path: established JPEG EXIF orientation and resizing rather than handwritten image algorithms; x/image supplies WebP decoding. Imaging's age is an explicit maintenance risk. Only supported formats and bounded inputs enter decoding. Its JPEG-only EXIF handling must not silently ignore orientation-bearing PNG/WebP metadata; those unsupported combinations must fail explicitly unless a tested normalizer supports them. |
| `golang.org/x/image v0.45.0` with standard codecs only | Same maintained Go module and toolchain compatibility. | Good decode/resize primitives, but no complete EXIF auto-orientation boundary. Would require additional orientation parsing/transforms or rely solely on upstream-normalized previews; less complete than the requested normalization contract without more work/dependencies. |
| `github.com/h2non/bimg v1.1.9` / libvips | Wrapper is MIT, latest tag April 2022, repository last pushed January 2025, approximately 3034 stars. libvips is a separately maintained native dependency. | Broad image processing and orientation support, but introduces CGO/native runtime/build dependencies into the current pure-Go backend packaging. More deployment and codec maintenance than this bounded preview workflow needs. |
| Reuse existing Node `sharp v0.34.5` | Already installed through Next.js; Apache-2.0 wrapper with native libvips dependencies. | Provides the relevant transformations without introducing another image library family. However, Go jobs would need a new internal call to the Node service or a Node runtime in the backend. This adds deployment and request-lifecycle coupling; the current Next.js image optimizer is not the authorized, transient AI preparation boundary required by CH08. |

The approved version set also requires updating existing `golang.org/x/text` from v0.32.0 to **v0.41.0** and `golang.org/x/sys` from v0.39.0 to **v0.47.0**, as declared by x/image v0.45.0. Both declare Go 1.25.0; the application toolchain remains Go 1.25.14. These transitive changes were included in the dependency-choice disclosure. Application resolution additionally requires existing `golang.org/x/sync v0.22.0` through x/text v0.41.0; this was reported during implementation and is covered by the race/regression gates.

Before committing an approved choice, verify checksums, run the applicable dependency vulnerability audit, exercise all orientation states and malformed/bounded inputs, verify CH07 language/country regressions under the updated x/text, and build/run the backend container. Repository activity and popularity are not security proofs; the limited preliminary audit below does not replace application verification.

Evaluation evidence: an isolated temporary Go 1.25.14 module using the recommended imaging/x/image versions passed `go mod verify` and compilation. `govulncheck v1.7.0 -show verbose` reported no vulnerabilities for that sample's decoder/resize/JPEG-encoder call graph and its three scanned modules, including the sample module. This is a preliminary dependency evaluation, not an application-wide audit or completed CH08 security verification. The application's module/checksum files were unchanged during evaluation.
