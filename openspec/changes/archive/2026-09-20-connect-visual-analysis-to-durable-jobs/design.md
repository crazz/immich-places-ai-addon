## Goals / Non-Goals

**Goals:** One authorized Visual job can execute asynchronously, survive restart, stop safely and retain results while respecting finite resource reservations.

**Non-Goals:** No launch UI, Context-assisted execution, generic queue service, new dependency, automatic retention, Research, writeback or live deployment. Keep default AI disablement. GATE-04 operating/retention decisions and reference-NAS measurements remain release prerequisites; fixtures can implement the explicit contracts below.

## Decisions

### Admission and public contract

Use thin root `aiJobHTTP*.go` handlers with the existing session, exact Origin, bounded JSON and no-store conventions. Register `/ai/jobs` and `/ai/jobs/` before the broad provider handler. Core admission/execution policy belongs in `internal/ai/jobs`; root adapters own SQLite and composition of the selection, image and analysis consumers. No transaction spans network work.

`POST /ai/jobs` accepts a selection token, idempotency key, exact profile/revision, `visual` mode, strict/explicit-JSON format, languages/primary language, versioned image-consent binding and finite limits. It never accepts an authoritative owner or replacement asset list. Cap the body at 32 KiB. Require current enabled profile revision, applicable image/format observations, production token policy and a current locally revalidated snapshot with 1–500 eligible assets. Persist the exact manifest/filter metadata and membership, consent, model, format, policy identities and limits atomically. Reject the whole new submission when snapshot facts changed; do not silently narrow or expand it.

Close the read-to-submit race by sharing owner/installation/snapshot revalidation with the short admission transaction, rather than invoking the existing loader and trusting its earlier transaction. Retain each member's available raw capture timestamp and the explicitly selected album ID/label as local admission provenance for history filters; absent values remain absent, and Visual never sends them to the provider. No provider, image or upstream per-asset call runs during admission. Current upstream authorization occurs at execution. Return `202` plus job ID after commit; reference target is under two seconds for 500 items, to be measured separately. New keys require valid snapshots. An identical retry of an already admitted key returns its existing job even after snapshot expiry, using the retained normalized request fingerprint; changed input conflicts. Disablement still rejects new submission requests and cannot restart the worker through a duplicate POST.

`GET /ai/jobs/{id}` returns immutable request summary, aggregate item counts, call/token accounting and at most 500 safe item summaries, including result IDs. `GET /ai/jobs?limit=&cursor=` lists private current-installation summaries, default 20/max 100, ordered by creation time and ID with an opaque owner/filter-bound cursor. This allows CH13 recovery after refresh without browser-local IDs being authoritative. `POST /ai/jobs/{id}/cancel` is idempotent and uses the same mutation protection. Reads/cancel remain available when AI execution is disabled; they never enable dispatch. Foreign IDs return the same unavailable response as absent IDs. Errors use stable safe categories, request IDs and retryability, never raw provider bodies.

Accepted jobs use their own retained membership and consent after admission; selection-token expiry or snapshot cleanup must not invalidate queued work. Current per-asset access/eligibility still gates execution. Source verification confirms image preparation checks current installation/asset authority without loading the expiring selection token. Keep that separation in the new consumer and test execution after snapshot cleanup.

### Explicit production token policy and accounting

Introduce backend-only `AI_EXECUTION_POLICIES` JSON entries, empty by default. Each entry binds installation, owner, profile ID/revision, model and egress-policy identity to one approved output-limit field (`max_tokens` or `max_completion_tokens`), a positive maximum output allowance and a conservative maximum input-token allowance for the bounded image/prompt envelope. Include a policy version, evidence reference and optional currency/input/output tariff values. This is an operator-attested compatibility/accounting policy, visibly distinct from CH03's observed image/format report; saving a profile or reading policy performs no probe. Invalid, duplicate or incomplete entries fail configuration validation. No guessed token field, model tokenizer or new dependency is introduced.

An entry is usable only when its documented input bound covers the entire enforced request envelope, including image processing, schema and controlled instructions. Enforce its request-byte/image limits before dispatch, and reject an unsupported envelope. Policies cannot enlarge CH08/CH09 limits. Runtime policy identity changes block unfinished work until an explicit new submission. Provide a safe readiness projection through the existing private profile read DTO for CH13; never expose credentials or evidence documents. A policy asserts a provider contract, not independent proof of actual billing. Validate it using synthetic fixtures and require deployment-specific evidence before live activation.

Persist per-attempt reservations with lease identity before the provider boundary. In one transaction reserve one call and the entire configured input allowance plus chosen output ceiling against item/job limits; all numbers are positive bounded integers with checked arithmetic. Job call limit is at most three times item count; default one call allowance per selected item, with retries consuming the same finite pool. Per-item claims/calls remain at most three. Require `maxTokens` to cover at least one attempt; jobs may stop partially when the user chooses a smaller total allowance than the whole batch requires. The output ceiling is sent only using the exact approved field.

Keep reserved token allowance consumed for the retained job even when reported usage is smaller, absent, malformed, or a response is lost. Record trustworthy provider-reported usage separately, including explicit unknown status. This conservative ledger cannot overspend its own allowance through concurrency or retry refunds. If reported usage exceeds the attested bound, block the job and mark policy evidence invalid for new dispatch; do not claim to undo provider charges. Monetary reservation is an estimate derived from the same allowance and configured tariffs; an optional estimate cap is accepted only with complete tariffs, never advertised as a billing guarantee. Unknown tariffs produce unknown cost, not zero. Never store image bytes or raw responses.

### Worker lifecycle, authority and failure translation

Compose the real executor from read-only image preparation, Visual analysis and durable guards. Use the existing defaults: two global/one per-owner leases, 180-second expiry, a 30-second heartbeat, 120-second total attempt deadline and at most three claims/calls per item. Add bounded backend configuration validated against core policy limits. Run a fixed-size worker loop with a one-second idle delay and bounded recovery, not one goroutine per item. All workers share the application shutdown context and are joined; no request context owns an accepted job. Browser closure/session expiry does not revoke accepted consent; account, installation, upstream access, provider revision/enablement, destination policy and job cancellation still govern each attempt.

Combine lease authority with exact active provider revision, current image/source authority, consent and budget policy before preparation, after DNS resolution immediately before reservation/dispatch, and before publication. Never replace a stale source/profile with a newer one. Cancellation/disablement prevents new calls; an in-flight request may already have incurred usage, but cannot publish after losing authority. Revalidate canonical Visual output with empty evidence and atomically store the existing immutable result plus admission/usage provenance.

Translate timeout, bounded 429/5xx and retryable transport failures to the existing transient policy; invalid image/contract/refusal/truncation to permanent safe item failures; authentication, unavailable model, revoked consent/profile or policy mismatch to a systemic job block. Missing/deleted target access fails only that item unless owner/installation authority is lost. SQLite/lease failures retain CH11 recovery semantics. Do not introduce transport retries, format fallback, repair calls or duplicate reservation layers. Retain charges for any reservation whose dispatch outcome is unknown.

### Persistence, verification and rollout

Use additive migrations allocated at implementation time for admission provenance, policy/limit fields and attempt reservations/usage. Preserve existing immutable results. Mark pre-integration jobs without production admission metadata ineligible for the real executor; retain their history and do not infer consent during upgrade. New writes use a versioned envelope. Rollback first disables workers and backs up SQLite/key material; restore a compatible backup when reverting schema expectations, rather than destructively downgrading active job data.

Verification follows Plus TDD and scenario mapping: real SQLite for atomic admission/idempotency/reservations/upgrades/reopen, competing workers for caps/fencing, authenticated HTTP fixtures for route protection, synthetic provider/Immich services for actual end-to-end execution and zero mutations. Exercise unknown usage, consumed reservations after timeout, changed policy/profile/source, shutdown/restart and 500-item bounded responses. Run shared size/boundary/coverage/race/frontend/browser/build gates and Docker packaging during apply; preserve manual/GPX and capability-test behavior. Measure NFR-04/05 on approved reference hardware separately. No current document or fixture result closes live compatibility, quality or retention approval gates.

## Risks / Trade-offs

- Conservative token reservations can stop a batch despite lower reported usage; predictable admission takes precedence over reclaiming uncertain usage.
- Operator-attested token bounds depend on provider behavior; unknown support fails closed and violated bounds stop later calls, without claiming exact billing control.
- Local snapshot admission cannot prove current upstream access; each real attempt rechecks it before disclosure.
- Crash after dispatch can cause a bounded retry and a second charge; immutable completion and lease fencing do not imply exactly-once billing.
- A production consumer expands reachable behavior; keep it disabled by default and require the separate operational release decisions before activation.
